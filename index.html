01 / 06

Git a prvý commit

Čo Git vlastne robí a ako uložiť prvú verziu projektu.

Poznáš toto?

Takto vyzerá verzovanie bez Gitu: kopírovanie. Každá „finálna“ verzia dostane nový súbor a po týždni už nikto nevie, ktorá je tá správna.

Ktorá verzia je tá správna? Čo sa medzi nimi zmenilo? Kto mi prepísal môj kód? Presne tento chaos Git rieši.

TK

Skoro každý má niekde priečinok plný zipov s menami ako final_NAOZAJ. Z neho nezistíš, čo sa zmenilo, kto to zmenil, ani ktorá verzia je posledná. Ak máš doma podobný priečinok, nie si sám.

Git je fotoalbum tvojho projektu

Git je systém na správu verzií. Namiesto kopírovania zipov si robíš snímky projektu. Takej snímke sa hovorí commit.

  • Snímka je commit. Uloží stav všetkých súborov aj s popisom: kto, kedy a prečo.
  • Funguje lokálne. Celá história je na tvojom počítači v skrytom priečinku .git, aj bez internetu.
  • Návrat kedykoľvek. Vieš sa pozrieť na ľubovoľnú starú verziu alebo ju obnoviť.

Priečinku, ktorý Git sleduje, hovoríme repozitár, skrátene repo. Každý commit má jedinečný kód, takzvaný hash, napríklad a3f9c21.

TK

Prečo Git? Aby si sa nebál nič pokaziť. Každý commit je bod, ku ktorému sa vieš vrátiť. Bez neho experimentuješ so strachom, s ním pokojne.

Git nie je GitHub

Git je program na tvojom počítači. Sleduje zmeny v súboroch, funguje aj bez internetu a ovládaš ho príkazmi alebo v editore.

GitHub je webová služba. Uchováva kópiu repozitára online, umožňuje zdieľanie a spoluprácu v tíme a pridáva pull requesty, review a issues. Podobne fungujú GitLab a Bitbucket.

Git je fotoaparát. GitHub je online album, kam fotky nahráš a ukážeš ich ostatným.

TK

Toto je asi najčastejšia zámena na začiatku. Git funguje úplne sám, aj keď GitHub nikdy nepoužiješ. GitHub je len miesto, kam si repozitár odložíš online a kde s ním pracuje celý tím. Ak by zajtra zmizol, tvoja história ostane celá na tvojom disku.

Každá zmena prejde tromi miestami

Kým zmenu uložíš do histórie, prejde tromi miestami.

Pracovný priečinok sú súbory, ktoré práve upravuješ, ako veci rozložené na stole. Staging sú zmeny vybrané na uloženie, ako veci vložené do krabice. Repozitár sú uložené snímky, teda commity, ako zalepená krabica so štítkom.

Staging ti dovolí uložiť len časť zmien, napríklad dva súbory z piatich, a zvyšok nechať na neskôr.

TK

Toto je najdôležitejší obrázok celej prezentácie. Upravuješ súbory na stole, vyberieš, čo chceš uložiť, a potom to zapečatíš commitom do histórie. Keď pochopíš tieto tri miesta, zvyšok Gitu do seba zapadne.

Začíname: založ repozitár

Repozitár je obyčajný priečinok, v ktorom Git sleduje zmeny. Vo VS Code na to stačí jedno tlačidlo, v termináli jeden príkaz.

VS Code

  1. Otvor priečinok projektu cez File → Open Folder…
  2. Otvor Source Control ikonou vľavo alebo cez Ctrl+Shift+G (na Macu ⌃+⇧+G).
  3. Klikni na Initialize Repository. Priečinok je odteraz repozitár.

Terminál

# raz na počítači: kto si
git config --global user.name "Ján Novák"
git config --global user.email jan@mail.sk
# hlavná vetva sa bude volať main
git config --global init.defaultBranch main
# git pull pri rozdielnej histórii spraví merge
git config --global pull.rebase false
# správy commitov sa otvoria vo VS Code, nie vo Vime
git config --global core.editor "code --wait"

# v priečinku projektu
cd moj-web
git init
git status

git config nastavíš len raz. Meno a e-mail sa zapíšu ku každému tvojmu commitu, ďalšie tri riadky ti ušetria prekvapenia neskôr. Na Macu musí byť príkaz code dostupný v termináli: vo VS Code spusti Shell Command: Install 'code' command in PATH.

TK

Pred prvým commitom treba Gitu povedať, kto si, a na to je git config. A git status si zapamätaj ako prvý príkaz vôbec: keď nevieš, čo sa deje, spusti ho.

Commit: ulož snímku projektu

Commit je uložená verzia projektu so správou, ktorá hovorí, čo sa zmenilo.

VS Code

  1. Zmenené súbory uvidíš v Source Control v sekcii Changes. U znamená nový súbor, M zmenený.
  2. Pri súbore klikni na + (Stage Changes). Presunie sa do Staged Changes.
  3. Do políčka napíš krátku správu, čo si urobil, napríklad Pridaj kontaktný formulár.
  4. Klikni na Commit, alebo stlač Ctrl+Enter (na Macu ⌘+Enter).

Ak nič nevyberieš a klikneš na Commit, VS Code sa opýta, či má uložiť všetky zmeny.

Terminál

# ukáže zmenené a nové súbory
git status
# alebo všetko naraz: git add .
git add contact.html style.css
git commit -m "Pridaj kontaktný formulár"

-m znamená message, teda krátka správa, ktorá ku commitu patrí.

TK

Commituj často. Malý commit sa dá ľahko pochopiť aj vrátiť. Commit so štyridsiatimi súbormi a správou „zmeny“ nevráti nikto.

Pozri sa do histórie

História sa číta zhora nadol: najnovší commit je hore. Pri každom vidíš správu, autora a čas.

VS Code

  1. V Source Control rozbaľ sekciu Graph.
  2. Klikni na commit a uvidíš, čo sa v ňom zmenilo.

Terminál

git log --oneline
# a3f9c21 Pridaj kontaktný formulár
# 7b2e410 Oprav chybu v menu
# 5d01c7e Pridaj menu
# 1c8d903 Prvá verzia webu

# ukáže presne, čo sa v commite zmenilo
git show a3f9c21

Každý commit má jedinečný hash. Na odkazovanie naň stačí prvých 7 znakov.

TK

Hash je ako rodné číslo commitu. Nikto si ho nepamätá celý, ale keď sa potrebuješ na commit odvolať, prvých sedem znakov stačí.

Dobrá správa ušetrí čas celému tímu

Commit správu čítaš o pol roka, keď hľadáš, kde sa niečo pokazilo. Preto ju píš tak, aby povedala, čo commit urobí.

Takto nieTakto áno
fixOprav pád formulára pri prázdnom e-maile
zmenyPridaj validáciu kontaktného formulára
asdfghZmeň farbu tlačidiel podľa nového dizajnu
piatok večer 2Odstráň nepoužívané CSS štýly
  • Píš, čo commit urobí. Začni slovesom: Pridaj…, Oprav…, Odstráň…, Zmeň…
  • Jeden commit, jedna zmena. Malé commity sa ľahšie čítajú, kontrolujú aj vracajú.
TK

Jednoduché pravidlo: správa je pokyn, čo commit urobí, napríklad „Pridaj validáciu formulára“. A ak v nej potrebuješ slovo „a“, väčšinou to mali byť dva commity.

02 / 06

Vetvy a merge

Paralelná práca a jej spájanie.

Vetva: bezpečné miesto na experimenty

Vetva (branch) je samostatná línia commitov. Hlavná vetva sa volá main a je v nej stabilná verzia, tá, ktorú vidia používatelia.

Keď robíš niečo nové, odbočíš na vlastnú vetvu, napríklad feature/login. Je to tvoja dielňa: čo tu rozbiješ, main neovplyvní. Každá úloha má vlastnú vetvu, takže ich môže byť viac naraz: feature/… na nové veci, fix/… na opravy.

TK

Na maine priamo nerob. Main je to, čo funguje. Všetko nové patrí na vlastnú vetvu a do mainu to ide až vtedy, keď je to hotové. Vetva je zadarmo, tak sa nimi nešetri.

Vytvor vetvu a prepínaj sa medzi nimi

VS Code

  1. Klikni na názov vetvy vľavo dole v stavovom riadku, napríklad main.
  2. Vyber + Create new branch…
  3. Zadaj názov, napríklad feature/login. VS Code ťa na novú vetvu rovno prepne.
  4. Späť na main sa dostaneš rovnako: klik na názov vetvy a vyber main.

Terminál

# zoznam vetiev, aktuálna má hviezdičku
git branch
# vytvor vetvu a prepni sa na ňu
git switch -c feature/login
# späť na main
git switch main

-c znamená create: vytvor vetvu a rovno sa na ňu prepni. V starších návodoch nájdeš git checkout -b, robí to isté.

TK

Hviezdička v git branch ukazuje, na ktorej vetve práve si. Vo VS Code to vidíš stále vľavo dole. Zvykni si tam pozrieť skôr, ako začneš písať kód.

Merge spojí prácu z vetvy späť do mainu

Keď je práca na vetve hotová, chceš ju dostať do mainu. Tomu sa hovorí merge, po slovensky zlúčenie.

Ak sa obe vetvy medzitým zmenili, Git vytvorí merge commit s dvoma rodičmi. Výsledok: main obsahuje formulár aj opravu od kolegu.

Ak sa main medzitým nehýbal, Git ho len posunie dopredu na tvoj posledný commit. Tomu sa hovorí fast-forward. Po merge môžeš vetvu zmazať, práca ostáva v maine.

TK

Merge sa netreba báť. Ak niečo nesedí, Git ti to povie skôr, ako čokoľvek pokazí. A aj keď sa ti výsledok nepáči, je to len ďalší commit v histórii, ku ktorému sa vieš vrátiť.

Zmerguj vetvu do mainu

VS Code

  1. Prepni sa na main kliknutím na názov vetvy.
  2. V Source Control klikni na ··· (Viac akcií) → Branch → Merge…
  3. Vyber vetvu feature/login.

Terminál

git switch main
git merge feature/login
# po merge vetvu uprac
git branch -d feature/login
# história ako graf
git log --oneline --graph

Pozor: merguješ vždy do vetvy, na ktorej práve stojíš.

TK

Najčastejšia chyba začiatočníkov: zabudnú sa prepnúť na main a mergujú opačným smerom. Najprv sa prepni na cieľovú vetvu, až potom merguj tú, ktorú chceš pridať.

Konflikt: dve zmeny v tom istom riadku

Väčšinou Git zlúči zmeny sám. Konflikt vznikne, keď dve vetvy zmenia ten istý riadok inak. Git nevie, ktorá verzia je správna, tak ich v súbore index.html označí značkami:

<<<<<<< HEAD
<h1>Vitajte na našom webe</h1>
=======
<h1>Ahoj, vitaj u nás!</h1>
>>>>>>> feature/uvod

Hore, pod HEAD, je to, čo je na tvojej vetve. Dole, až po feature/uvod, je to, čo prichádza. Vyberieš jednu verziu, obe, alebo to prepíšeš ručne, a značky zmažeš.

VS Code

  1. Súbor s konfliktom nájdeš v Source Control pod Merge Changes.
  2. Nad konfliktom klikni na Accept Current Change, Accept Incoming Change alebo Accept Both Changes. Pri zložitejšom konflikte pomôže Resolve in Merge Editor.
  3. Ulož súbor, klikni na + a potom na Continue. Tým sa merge dokončí.

Terminál

git merge feature/uvod
# CONFLICT (content): Merge conflict in index.html
# uprav súbor a zmaž značky, potom:
git add index.html
git commit --no-edit
# alebo všetko zruš a vráť sa pred merge:
# git merge --abort
TK

Konflikt nie je chyba. Git sa len pýta: ktorú verziu chceš? Najčastejší omyl je kliknúť na Accept Both bez čítania a potom mať v kóde obe verzie pod sebou. Vždy si pozri, čo vlastne ostalo.

03 / 06

GitHub a pull requesty

Push, pull a spolupráca cez pull requesty.

Tvoj počítač, GitHub a kolegovia

Každý má na svojom počítači celú kópiu repozitára. GitHub je spoločné miesto uprostred. Kópii na GitHube sa hovorí remote a štandardne sa volá origin.

Dôležité: commit sa deje len u teba. Na GitHub sa dostane až po push. Novinky od kolegov získaš cez pull.

TK

Tu sa veľa ľudí zamotá. Commitol som, tak prečo to kolega nevidí? Lebo commit je zatiaľ len na tvojom disku. Kým nespravíš push, GitHub o ňom nevie.

Dva spôsoby, ako začať s GitHubom

Buď máš projekt u seba a chceš ho dostať na GitHub, alebo už na GitHube je a chceš si ho stiahnuť k sebe.

A. Projekt mám u seba, chcem ho nahrať na GitHub

VS Code

  1. V Source Control klikni na Publish Branch a vyber GitHub. Ak priečinok ešte nie je repozitár, tlačidlo sa volá Publish to GitHub. Pri prvom použití ťa VS Code prihlási do GitHubu cez prehliadač.
  2. Vyber, či má byť repozitár verejný (public) alebo súkromný (private).

Terminál

# najprv vytvor prázdny repozitár na github.com
git remote add origin https://github.com/jan/web.git
git push -u origin main

-u origin main nastaví prepojenie raz. Potom už stačí písať len git push.

B. Projekt už je na GitHube, chcem si ho stiahnuť

VS Code

  1. Otvor paletu príkazov cez Ctrl+Shift+P (na Macu ⌘+⇧+P) a vyber Git: Clone.
  2. Vlož adresu repozitára z GitHubu a vyber priečinok, kam sa má stiahnuť.

Terminál

git clone https://github.com/jan/web.git
cd web
TK

Clone spravíš raz na začiatku, keď sa pridávaš k existujúcemu projektu. Publish alebo remote add, keď si projekt založil sám a chceš ho dať na GitHub. Viac na to nepotrebuješ.

Push posiela, pull sťahuje

Push pošle tvoje commity na GitHub. Pull stiahne commity, ktoré tam pribudli od ostatných, a zapracuje ich do tvojej vetvy. Fetch len zistí, čo je nové, a nemení tvoje súbory ani vetvy. Pull je vlastne fetch a hneď za ním merge.

VS Code

  1. Klikni na Sync Changes. Najprv stiahne novinky z GitHubu, potom pošle tvoje commity.
  2. Šípky pri tlačidle a v stavovom riadku ukazujú, koľko commitov čaká na stiahnutie a koľko na odoslanie.
  3. Novú vetvu, ktorá na GitHube ešte nie je, pošleš cez Publish Branch.

Terminál

# stiahne a zapracuje (fetch + merge)
git pull
# pošle tvoje commity na GitHub
git push
# len zistí, čo je nové, tvoje súbory nemení
git fetch

Zlaté pravidlo: pred prácou pull, po práci push.

TK

Push zlyhá, ak na GitHube medzitým pribudlo niečo, čo ty nemáš. Riešenie je jednoduché: najprv pull, potom push. Preto to zlaté pravidlo. A git push --force na zdieľanej vetve nepoužívaj, prepíše históriu aj ostatným.

Pull request je žiadosť o zlúčenie

Pull request, skrátene PR, nie je príkaz Gitu, je to funkcia GitHubu. Hovorí: tu je moja vetva, pozrite sa na ňu, a ak je v poriadku, zlúčte ju do mainu.

  1. Vetvacommity na feature/kontakt
  2. Pushvetva je už aj na GitHube
  3. Otvor PRnázov, popis, reviewer
  4. Reviewkolega komentuje a schváli
  5. Mergezmeny sa dostanú do mainu
TK

Pull request je najlepšie miesto na učenie. Keď ti niekto okomentuje kód, naučíš sa viac ako z hocijakého tutoriálu. A aj keď robíš sám, PR ti dá šancu pozrieť si celý rozdiel ešte raz, skôr ako ho pustíš do mainu.

Ako otvoriť pull request

Na GitHube

  1. Po push sa na stránke repozitára objaví žltý pruh s tlačidlom Compare & pull request.
  2. Napíš názov a popis, vpravo vyber Reviewers.
  3. Klikni na Create pull request. Po schválení ho zlúčiš tlačidlom Merge pull request.

Kto rád ostáva v editore, zvládne to isté vo VS Code s rozšírením GitHub Pull Requests.

Terminál (GitHub CLI)

gh pr create --base main --title "Kontaktný formulár" --body "Pridáva formulár a validáciu"
gh pr list
gh pr merge 42 --merge
# po merge si stiahni nový main
git switch main
git pull

gh je oficiálny nástroj GitHubu pre terminál. Inštaluje sa zvlášť a prihlásiš sa cez gh auth login.

TK

Nástroj gh si zapamätaj. O chvíľu uvidíš, že presne cez neho otvárajú pull requesty aj AI agenti.

04 / 06

Stash a záchranné brzdy

Odloženie rozrobenej práce a vrátenie zmien, keď sa niečo pokazí.

Odlož rozrobenú prácu do šuplíka

Robíš na formulári a zrazu príde správa: „Na webe je chyba, oprav ju hneď!“ Polovičnú prácu commitnúť nechceš. Zahodiť ju tiež nie. Na toto je stash.

  1. Odložgit stashRozrobené zmeny idú do šuplíka.
  2. Oprav chybugit switch mainOprava, commit, push.
  3. Vráť sagit switch -Späť na svoju vetvu. Pomlčka znamená predošlú.
  4. Vybergit stash popZmeny sú späť, pokračuješ ďalej.

Do šuplíka môžeš odložiť aj viac vecí naraz a vyberať ich neskôr.

TK

Stash je dočasná odkladacia schránka. Zoberie neuložené zmeny v súboroch, ktoré Git sleduje, odloží ich a priečinok vyčistí, takže sa môžeš pokojne prepnúť na inú vetvu. Len pozor, na šuplík sa rado zabúda.

Ako na stash

VS Code

  1. V Source Control klikni na ··· → Stash → Stash.
  2. Prepni vetvu, oprav chybu a commitni.
  3. Na svojej vetve daj ··· → Stash → Pop Latest Stash.

Nové súbory, ktoré Git ešte nesleduje, pribalíš cez Stash (Include Untracked).

Terminál

git stash
git switch main
# … oprava, commit, push …
git switch -
git stash pop
# čo všetko je v šuplíku
git stash list

Nové súbory pribalíš cez git stash -u.

TK

Pop vráti zmeny a zo šuplíka ich zmaže. Apply ich vráti a v šuplíku nechá. A ak máš niekedy pocit, že ti zmizla práca, skús najprv git stash list. Často tam celý čas čaká.

Keď sa niečo pokazí

Git má na väčšinu chýb záchrannú brzdu. Tieto budeš potrebovať najčastejšie:

SituáciaVS CodePríkaz
Zahodiť neuložené zmeny v súboreDiscard Changes (↶)git restore index.html
Vrátiť súbor zo staginguUnstage Changes (−)git restore --staged index.html
Doplniť niečo do posledného commituCommit ▾ → Commit (Amend)git commit --amend
Vrátiť commit, ktorý už je na GitHubenajjednoduchšie príkazomgit revert a3f9c21
Niektoré súbory nemajú ísť do Gituotvor súbor .gitignore a dopíš riadok .envecho ".env" >> .gitignore (bash, zsh)

Pozor: restore a Discard zahodia zmeny natrvalo. Revert je bezpečný: pridá nový commit, ktorý zmenu vráti.

TK

Amend používaj len na commit, ktorý ešte nie je na GitHube, inak prepisuješ históriu, ktorú už majú aj ostatní. Pre commity, ktoré už sú hore, je správna cesta revert. A do .gitignore patria heslá, súbor .env a priečinky ako vendor alebo node_modules.

05 / 06

Zhrnutie

Celý postup na jednom obrázku a ťahák.

Celý postup na jednom obrázku

Takto vyzerá bežný deň s Gitom. Kroky 1 až 5 sa dejú u teba na počítači, kroky 6 až 8 na GitHube.

  1. Stiahni novinkygit pullaktuálny main
  2. Nová vetvagit switch -c …pre každú úlohu
  3. Uprav kód(editor)píšeš a testuješ
  4. Priprav zmenygit add .„+“ vo VS Code
  5. Ulož snímkugit commit -m "…"Commit vo VS Code
  6. Pošli na GitHubgit pushSync alebo Publish Branch
  7. Pull requestgh pr createpopis a review
  8. Merge do mainugh pr mergea vetvu zmaž

u teba na počítači na GitHube. Potom znova od začiatku s ďalšou úlohou.

TK

Toto je celý deň v ôsmich krokoch: pull, nová vetva, práca, add, commit, push, pull request s review a merge. Ak si z dnešku zapamätáš len päť príkazov, nech sú to status, add, commit, push a pull.

Ťahák: VS Code a príkazy vedľa seba

To isté cez AI agentov

To isté, ale cez konverzáciu.

Tri spôsoby, ten istý Git

  • VS Code Klikáš na tlačidlá. „+“ → Commit → Sync
  • Terminál Píšeš príkazy. git commit -m "…"
  • AI agent Opíšeš, čo chceš. Agent spustí príkazy, ty ich skontroluješ. „Commitni to a otvor PR.“

Agentom môže byť napríklad Claude Code, OpenAI Codex alebo GitHub Copilot v režime agenta. Pod kapotou robí presne to, čo sme sa práve naučili.

TK

Agent je program s jazykovým modelom, ktorý vie sám spúšťať príkazy v termináli, čítať a upravovať súbory. Nepíšeš mu git príkazy, ale zámer. On ich vymyslí a spustí, ty sleduješ a schvaľuješ. Na konkrétnom nástroji až tak nezáleží, princíp je rovnaký.

Rozhovor 1: nová vetva a commit

Ty

Vytvor vetvu feature/kontakt a do contact.php pridaj kontrolu, či je e-mail zadaný správne. Potom to commitni.

Agent

Vytváram vetvu a upravujem formulár.

git switch -c feature/kontakt

# upravený contact.php (+14 −2)

git add contact.php

git commit -m "Pridaj validáciu e-mailu"

Hotovo: commit a3f9c21 je na feature/kontakt. Pushnúť na GitHub?

  • Zadanie je konkrétne: vetva, súbor aj cieľ.
  • Agent spúšťa tie isté príkazy, ktoré už poznáš.
  • Pred push sa opýta. To je krok, ktorý ide von z tvojho počítača.
TK

Pozri sa na príkazy v odpovedi agenta. Sú to presne tie z predchádzajúcich častí, len ich nepíšeš ty. Dobrý agent sa pred krokom, ktorý mení niečo mimo tvojho počítača, ako je push, opýta. Dá sa to nastaviť aj ako pravidlo.

Rozhovor 2: push a pull request

Ty

Áno, pushni to a otvor pull request do mainu. Do popisu napíš, čo sa zmenilo a ako to otestovať.

Agent

Posielam vetvu na GitHub a otváram pull request.

git push -u origin feature/kontakt

gh pr create --base main --title "Validácia e-mailu vo formulári" --body "Čo sa zmenilo: … Ako testovať: …"

Pull request #42 je otvorený a čaká na review.

  • Stačí „Áno“. Agent vie, o čom sa bavíte.
  • Popis pull requestu napíše agent, ty ho len skontroluješ.
  • Review stále robí človek z tímu.
TK

Agent používa ten istý nástroj gh, ktorý sme videli pri pull requestoch. Veľká pomoc je, že napíše zmysluplný popis. Ale schválenie a merge je stále rozhodnutie ľudí v tíme.

Rozhovor 3: rýchla oprava a stash

Ty

Na maine je chyba: v pätičke sa zobrazuje zlý rok. Oprav to, ale nestrať moju rozrobenú prácu.

Agent

Odložím tvoje zmeny a chybu opravím na novej vetve.

git stash

git switch main && git pull

git switch -c fix/rok-v-paticke

# upravený footer.php (+1 −1)

git commit -am "Oprav rok v pätičke"

git switch feature/kontakt && git stash pop

Oprava je na fix/rok-v-paticke a tvoja práca je späť. Otvoriť aj pull request?

  • Ty si povedal čo. Agent vymyslel ako.
  • Oprava má vlastnú vetvu a nemieša sa s formulárom.
  • Rozrobená práca sa nestratila: stash a stash pop.
TK

Toto je presne scenár zo stashu, ale celý ho za nás odohral agent. Všimni si, že som mu nepovedal slovo stash. Povedal som len cieľ, nestratiť rozrobenú prácu, a on si vybral správny nástroj.

Rozhovor 4: konflikt pri merge

Ty

Zmerguj main do mojej vetvy. Ak bude konflikt, najprv sa ma opýtaj.

Agent

git merge main

CONFLICT (content): Merge conflict in config.php

Konflikt v config.php: na maine sa zmenila adresa API, u teba timeout. Navrhujem ponechať obe zmeny. Súhlasíš?

Ty

Áno, ponechaj obe.

Agent

Konflikt vyriešený, merge dokončený (git add a git commit).

  • Pravidlo „najprv sa opýtaj“ dáš priamo do zadania.
  • Agent vysvetlí, čo sa zmenilo na ktorej strane.
  • Rozhodnutie ostáva na tebe.
TK

Konflikt je presne miesto, kde nechceš, aby agent rozhodol potichu. Preto mu to povieš rovno v zadaní. Agent konflikt prečíta, vysvetlí ľudskou rečou a navrhne riešenie. Ty len potvrdíš.

Štyri pravidlá dobrej spolupráce

  • Buď konkrétny. Povedz vetvu, súbor aj cieľ. Áno: „Pridaj validáciu e-mailu do contact.php.“ Nie: „Sprav to nejako lepšie.“
  • Stanov hranice. „Nepushuj bez opýtania.“ „Nikdy nerob force push na main.“ Trvalé pravidlá zapíš do súboru AGENTS.md alebo CLAUDE.md v projekte.
  • Kontroluj výsledok. Pred schválením si pozri git diff a pull request. Agent sa môže mýliť.
  • Malé kroky. Jedna úloha, jedna vetva, jeden pull request. Menšie zmeny sa ľahšie kontrolujú.
TK

AGENTS.md alebo CLAUDE.md je obyčajný textový súbor v koreni projektu, ktorý si agent prečíta na začiatku každej práce. Patria tam pravidlá ako pomenovanie vetiev, zákaz force push alebo štýl commit správ. Napíšeš ich raz a nemusíš ich opakovať v každom zadaní.

Kedy čo použiť

Neexistuje jediný správny spôsob.

  • VS Code Keď chceš vidieť zmeny, riešiť konflikty a ešte sa učíš.
  • Terminál Keď chceš rýchlosť a presnosť, na serveri alebo v skriptoch.
  • AI agent Keď má úloha viac krokov: vetva, commity, push, pull request. Vždy s tvojou kontrolou.

Agent píše príkazy za teba. Pochopenie a kontrola ostávajú na tebe.

TK

Preto sme sa najprv učili základy. Bez nich nevieš skontrolovať, čo agent spravil, a nevieš ho opraviť, keď sa pomýli. Kto rozumie vetvám, commitom a pull requestom, ten agenta riadi. Kto nie, ten sa len pozerá.

Domáca úloha: vyskúšaj si to

Prejdi celý postup sám a potom ho zadaj AI agentovi. Porovnaj, čo spravil.

  1. Repozitárzalož ho vo VS Code alebo cez git init
  2. Tri commitymalé, s dobrými správami

  4. Mergevetvu zlúč do mainu
  5. Pull requestprvý vlastný na GitHube
  6. S agentomto isté ešte raz a porovnaj
TK

Domáca úloha je jednoduchá: repozitár, pár commitov, vetva, merge a prvý pull request. Potom presne to isté zadaj agentovi a porovnaj výsledok. Keď niečo nebude jasné, napíš mi.

Kvíz, 6 otázok

Otestuj sa

Pri každej otázke je správna práve jedna odpoveď. Po kliknutí hneď uvidíš, či si trafil, a prečo.

Otázka 1 zo 6

Čo spraví git add contact.html?

git add presúva zmeny do stagingu, teda „do krabice“. Uloží ich až git commit a na GitHub ich pošle git push.

Otázka 2 zo 6

Aký je rozdiel medzi Gitom a GitHubom?

Git je fotoaparát, GitHub je online album. Git beží lokálne a internet nepotrebuje.

Otázka 3 zo 6

Chceš zlúčiť feature/login do mainu. Kde musíš stáť, keď spúšťaš merge?

Merguješ vždy do vetvy, na ktorej práve stojíš. Najprv git switch main, potom git merge feature/login.

Otázka 4 zo 6

Pri merge vznikol konflikt. Čo to znamená?

Konflikt je otázka, nie chyba. Vyberieš, čo ostane, zmažeš značky, súbor pridáš cez git add a commitneš.

Otázka 5 zo 6

Robíš na formulári a musíš hneď opraviť chybu na maine. Rozrobenú prácu commitnúť nechceš. Čo spravíš?

Stash odloží rozrobenú prácu do šuplíka, takže môžeš s čistým priečinkom prepnúť vetvu. Pop ti ju potom vráti.

Otázka 6 zo 6

Chceš, aby AI agent pridal do projektu novú funkciu. Čo je najrozumnejšie spraviť predtým?

Posledný commit je bod, ku ktorému sa vrátiš, ak agent niečo pokazí. Vlastná vetva drží jeho prácu mimo mainu, kým ju neskontroluješ.
